## Summary for the author

Hi @dvaldes, I've reviewed your PR and I think it covers a lot of the task. However, I found some aspects that can be improved, and others that must be corrected because they can affect operations and expose information. These must be fixed before merge:

1. **The live webhook secret is in `application.yml`.** It is now in the branch history, so please **ask Austral to rotate it today**, whatever happens to this PR (#1).
2. **The signature check is skipped when the header is missing**, so anyone can create payments (#2).
3. **Payer name, RUT and email are logged** (#3).
4. **A notification can be lost after we answer `200`**: it waits in an in-memory queue, and any error is swallowed (#4, #5).
5. **A late `PAYMENT_CONFIRMED` can overwrite a `PAYMENT_REVERSED`.** Salesforce would then reinstate a policy whose money was returned (#6).

Most of these problems could be solved with a change of approach. For example, verify the signature and then **store the notification durably before answering** (in a queue or a database, not in memory). Process the notification from there, with retries and a dead-letter queue. Then write to Salesforce with an **upsert by `Payment_Key__c`**, making sure stale states are discarded. If you like, we can go through it together. I have also left some notes on the tests, which currently pass even when the code is wrong (#12).

## What looks good

- **The goal is the right one.** Replacing the nightly import for Chile takes a customer's reinstatement from up to 48 hours to near real time.
- **The structure is clear.** The controller, the signature verifier, the service and the repository each have a single job, and dependencies are injected through constructors into `final` fields.
- **The signature follows the Austral spec**: HMAC-SHA256, lowercase hex, and the `X-Austral-Signature` header.
- **`eventId` is the right idempotency key for Austral**, because it is stable across retries. It is backed by a primary key in `processed_notification`.
- **The event types are mapped to the statuses of the data model** (`Captured`, `Failed`, `Refunded`), as `DATA_MODEL.md` defines them.
- **The description is transparent.** It states what is still pending (the secret in Key Vault) and how the change was tested.
